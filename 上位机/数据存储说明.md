# 实验数据存储说明

> 本文档描述本系统**实际落盘的数据结构、命名规则与写入逻辑**。
> 所有内容都与 `ivcore/storage.py` 的实现逐条对应，不是设想稿。
>
> 适用版本：v0.4.5 及以后（温度并入主 CSV）
> 代码位置：`上位机/ivcore/storage.py`（写入）、`上位机/ui/buffer.py`（读取）

---

## 一、总体设计：双写 + 多分辨率

```
                      ┌──────────────────────────────┐
   每轮测量完成 ──────►│  SQLite（主存储，长表 + 宽表）│  ← 断电安全、可追溯
   (约 2~3 秒一轮)     └──────────────────────────────┘
                      ┌──────────────────────────────┐
                      │  CSV（实时副本，一行一轮）    │  ← 边测边写、可直接用 Excel 打开
                      └──────────────────────────────┘
                      ┌──────────────────────────────┐
                      │  聚合表 agg_1min / agg_1hour │  ← 7 天视图查询 <10 ms
                      └──────────────────────────────┘
```

**为什么要两份？**

| 存储 | 优点 | 缺点 | 用途 |
|---|---|---|---|
| **SQLite** | 断电不损坏、支持复杂查询、有索引 | 需要 SQL 或程序读取 | **权威数据源**，长期归档 |
| **CSV** | 任何软件都能打开、纯文本可 diff | 无索引、文件变大后慢 | **实时副本**，快速查看/导入 Excel |
| **聚合表** | 查询极快（毫秒级） | 丢失细节（只有 min/max/avg） | 画 1 天/7 天长期趋势图 |

程序关闭时会**校验两者轮数是否一致**，不一致就以数据库为准重写 CSV（见第八节）。

## 二、目录结构

```
D:\IV_data\                          ← 根目录（config.yaml 里 storage.dir）
├── 2026-10-28\                      ← 一天一个目录，日期格式 YYYY-MM-DD
│   ├── 2026-10-28.db                ← 当天数据库（SQLite，WAL 模式）
│   ├── 2026-10-28.db-wal            ← WAL 预写日志（运行时存在，属正常）
│   ├── 2026-10-28.db-shm            ← WAL 共享内存（同上）
│   ├── 2026-10-28_samples.csv       ← ★ 主数据 CSV（一行一轮，含温度）
│   └── 2026-10-28_env.csv           ← 【已废弃】旧版独立温度 CSV
├── 2026-10-29\
│   └── ...
└── 2026-10-30\
    └── ...
```

### 命名规则

| 规则 | 说明 |
|---|---|
| **日期零填充**（`2026-10-05` 而非 `2026-10-5`） | 保证**字符串排序 == 时间排序**，跨天合并时直接 `sorted()` 即可 |
| 文件名 = 目录名 + 后缀 | `2026-10-30.db`、`2026-10-30_samples.csv` |
| `_oldformat.csv` | 表头不兼容时**自动归档**的旧文件（见第七节） |
| `_env.csv` | v0.4.0 后温度已并入主 CSV，此文件**不再生成**；历史文件保留不动 |

> **为什么按天分库？**
> 1. 单库不会无限膨胀（7 天 × 3 秒 ≈ 20 万轮 ≈ 160 万测量点/库）
> 2. 跨天时自动切库，查询"某一天"只扫一个文件
> 3. 单个库损坏不影响其它天

## 三、CSV 主数据格式（`YYYY-MM-DD_samples.csv`）

### 列定义

```csv
iso_time,round_id,v1,i1,v2,i2,v3,i3,v4,i4,t1,t2,dt
2026-10-30 00:00:00,48680,8.84601e-05,-3.72304e-11,5.46703e-05,-4.43628e-11,0.00124852,2.07607e-10,3.05305e-05,-3.52628e-11,28.50,15.10,13.40
2026-10-30 00:00:03,1,4.89714e-05,-4.16388e-11,-3.24822e-05,-3.08172e-11,0.00125577,2.02092e-10,-4.06325e-05,-2.00632e-11,28.50,15.10,13.40
```

| 列 | 类型 | 单位 | 说明 |
|---|---|---|---|
| `iso_time` | 文本 | — | **网格时刻**，格式 `YYYY-MM-DD HH:MM:SS`，**只到秒** |
| `round_id` | 整数 | — | 轮号，**同一天内从 1 连续递增**（跨天重置、跨重启不重置） |
| `v1`…`v4` | 浮点 | **V** | 第 1~4 路开路电压 Voc |
| `i1`…`i4` | 浮点 | **A** | 第 1~4 路短路电流 Isc |
| `t1` | 浮点 | **℃** | 温度采集器通道 1 |
| `t2` | 浮点 | **℃** | 温度采集器通道 2 |
| `dt` | 浮点 | **℃** | 温差 `t1 - t2`（程序自动算，不是另一次测量） |

### 四条关键规则

**① 一行 = 一轮 = 一个时刻的全部数据**

电学量和温度**在同一次采样里取**（程序先测完 8 项，写盘前读一次温度），所以它们共用一个 `iso_time`，**天然同轴**。画图时直接用 `iso_time` 作唯一自变量即可。

**② 时间列严格等间隔**

`iso_time` 用的是「网格时刻」`t_grid0 + n × 采样间隔`，**不是**各测量点的物理时刻。所以：

```
00:00:00 → 00:00:03 → 00:00:06 → 00:00:09   （间隔 3 s 时）
差恒等于采样间隔，绝不会因为某一轮慢了而出现"3 秒 / 3.02 秒 / 2.98 秒"的抖动
```

真实耗时（含滞后）记录在数据库 `samples.ts` 和 `round_log` 里，需要精确时序时查那里。

**③ 空值 = 空白（不是 0）**

- 某项读数失败 → 该格**留空**
- 某轮整体失败 → 仍写一行（数据列全空），**保证时间列不断档**

> 这样画图时空值不会画成「0 V / 0 A」的假数据点。

**④ 数值格式**

| 列 | 格式 | 例子 |
|---|---|---|
| `v*` / `i*` | `%.6g`（6 位有效数字，自动科学计数法） | `8.84601e-05`、`1.41` |
| `t1` / `t2` / `dt` | `%.2f`（2 位小数） | `28.50`、`13.40` |

> `%.6g` 是为了**不丢有效数字**：电流量级从 pA 到 mA，固定小数位会失真。

## 四、数据库表结构

### 4.1 `samples` — 测量明细（长表，权威数据）

每个测量点一行（4 通道 × 2 模式 = 每轮 8 行）。

| 列 | 类型 | 说明 |
|---|---|---|
| `ts` | REAL | **物理测量时刻**（Unix 时间戳，微秒精度）—— 真实读数瞬间 |
| `grid_ts` | REAL | **网格时刻**（该点所属轮次，严格等间隔）—— CSV 的 `iso_time` 就是它 |
| `run_id` | INTEGER | 第几次运行会话（对应 `runs.id`） |
| `round_id` | INTEGER | 轮号（与 CSV 一致） |
| `ch` | INTEGER | 通道号 1~4 |
| `mode` | TEXT | `'V'`（电压）或 `'I'`（电流） |
| `value` | REAL | 数值 |
| `unit` | TEXT | `'V'` 或 `'A'` |
| `quality` | INTEGER | `0`=正常、`1`=可疑、`2`=无效（读数失败） |

**索引**：`ts`、`grid_ts`、`(ch, mode, ts)` 三个索引，覆盖常用查询。

### 4.2 `env_round` — 温度宽表（一行一轮）

| 列 | 类型 | 说明 |
|---|---|---|
| `grid_ts` | REAL **PK** | 与 `samples.grid_ts` 同值 → 可直接 JOIN |
| `run_id` | INTEGER | 运行会话 |
| `round_id` | INTEGER | 轮号 |
| `t1` | REAL | 温度通道 1（℃） |
| `t2` | REAL | 温度通道 2（℃） |
| `dt` | REAL | `t1 - t2`（℃） |

> 这张表等价于 CSV 的 `t1,t2,dt` 三列，但可以用 SQL 直接和电学量按轮关联：
> ```sql
> SELECT s.grid_ts, s.ch, s.mode, s.value, e.dt
> FROM samples s JOIN env_round e ON s.grid_ts = e.grid_ts;
> ```

### 4.3 `round_log` — 轮记录（一行一轮）

| 列 | 类型 | 说明 |
|---|---|---|
| `grid_ts` | REAL **PK** | 网格时刻 |
| `round_id` | INTEGER | 轮号 |
| `run_id` | INTEGER | 运行会话 |
| `n_ok` | INTEGER | 本轮成功读数个数（正常 8） |
| `n_bad` | INTEGER | 本轮失败个数 |

**作用**：记录**空轮**（整体失败的轮次在 `samples` 里没有任何行），有了这张表才能：
- 统计真实轮数
- 校验 CSV 完整性（第八节）
- 重建 CSV 时不丢空轮

### 4.4 `runs` — 运行会话

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER **PK** | 自增，就是 `samples.run_id` |
| `start_ts` | REAL | 程序开始采集的时刻 |
| `end_ts` | REAL | 停止采集的时刻（正常收尾才写） |
| `config_json` | TEXT | **当时的完整配置快照**（JSON） |

> `config_json` 非常重要：实验条件（采样间隔、时序参数、设备型号）会随时间变化，
> 三个月后回看数据时，只有这里能告诉你"当时是怎么测的"。

### 4.5 `events` — 事件日志

| 列 | 类型 | 说明 |
|---|---|---|
| `ts` | REAL | 事件时刻 |
| `level` | TEXT | `INFO` / `WARN` / `ERROR` |
| `src` | TEXT | 来源（`arduino` / `dmm` / `acq` / `tasensor` …） |
| `msg` | TEXT | 描述 |

典型内容：固件看门狗触发、单轮超时、温度读取失败、校验修复结果。

### 4.6 `env` — 【旧版】温度长表

v0.4.0 之前温度存在这里（长表：每通道一行）。**现在不再写入**，但表结构保留以兼容：
旧版数据仍在，读取代码会同时查 `env`（旧）和 `env_round`（新），保证历史曲线连续。

### 4.7 `agg_1min` / `agg_1hour` — 聚合表

| 列 | 类型 | 说明 |
|---|---|---|
| `bucket` | INTEGER | 时间桶的起点（Unix 秒，按 60 或 3600 取整） |
| `ch` | INTEGER | 通道号 |
| `mode` | TEXT | `'V'` / `'I'` |
| `v_min` | REAL | 桶内最小值 |
| `v_max` | REAL | 桶内最大值 |
| `v_avg` | REAL | 桶内平均值 |
| `n` | INTEGER | 桶内样本数 |
| — | PK | `(bucket, ch, mode)` |

**聚合规则**（`_agg_add` / `_flush_agg`）：

```
新样本进来 → 同时更新 1 分钟桶 和 1 小时桶（内存里累积）
每轮写完后 flush → 用 UPSERT 合并进表：
    v_min = MIN(旧值, 新值)
    v_max = MAX(旧值, 新值)
    v_avg = (旧avg × 旧n + 新avg × 新n) / (旧n + 新n)     ← 加权平均
    n     = 旧n + 新n
```

> **为什么不用 `AVG()` 直接算？**
> 7 天 × 3 秒 ≈ 20 万轮 × 8 = 160 万行，每次画图都全表扫描会卡死。
> 查聚合表是"每桶一行"（7 天 = 168 小时桶 / 10080 分钟桶），毫秒级返回。

**选源规则**（`buffer.pick_source`）：

| 视图跨度 | 数据源 | 原因 |
|---|---|---|
| ≤ 2 小时 | `samples`（原始） | 数据量小，要细节 |
| 2 ~ 40 小时 | `agg_1min` | 1440 个点够画 |
| > 40 小时 | `agg_1hour` | 最多 168 个点 |

## 五、时间戳模型（核心概念）

每轮有两个时间：

```
                    grid_ts（网格时刻）        ts（物理时刻）
                         │                        │
─────────────────────────┼──────┬────┬────┬──────┼──────────►  时间
                         │      │    │    │      │
                    本轮开始    第1项 第2项 ... 第8项
                      (t+0s)   (t+0.2s)        (t+1.6s)
```

| 时间 | 含义 | 存哪里 | 特点 |
|---|---|---|---|
| **`grid_ts`** | 本轮的"名义时刻"，`t_grid0 + 轮数 × 间隔` | CSV 的 `iso_time`、`samples.grid_ts`、`env_round.grid_ts`、`round_log.grid_ts` | **严格等间隔** |
| **`ts`** | 每个测量点的真实读数时刻 | `samples.ts` | 有抖动（每项间隔约 0.19 s） |

**为什么要两个？**

- 画图/FFT/统计分析要**等间隔**才能做 → 用 `grid_ts`
- 追溯"这一项到底什么时候测的"要**真实时刻** → 用 `ts`
- `ts - grid_ts` 的差值能反映测量滞后（一轮内最后一項约 +1.6 s）

**滞后保护**：如果某一轮严重超时（落后 ≥5 秒），程序会把 `t_grid0` 整体平移到当前时刻（`scheduler.py` 里 `drift` 补偿），避免为了追等间隔而疯狂补跑。

## 六、编号规则

### `round_id`（轮号）

| 规则 | 说明 |
|---|---|
| 从 **1** 开始 | 每天第一个轮次是 1 |
| **同一天内连续递增** | 中间不跳号（空轮也占号） |
| **跨重启不重置** | 启动时读 `MAX(round_id) FROM samples` 续上 |
| **跨天重置** | 新的一天从 1 重新开始（切库时自动处理） |

> ⚠️ **不要用 `round_id` 做全局唯一键** —— 跨天会重复。

> ⚠️ **历史数据注意**：v0.4.6 之前存在一个跨天轮号 bug —— `begin_round()` 在切库
> 之前就分配了轮号，导致零点那一轮带着昨天的大号（例如 `48680`），下一条又跳回 `1`。
> 该问题已修复（现在切库和分配轮号在同一时刻按 `grid_ts` 决定）。
> **此前的数据里可能看到轮号跳变，但数据本身没有丢失**，按 `grid_ts` 排序/关联即可。

### `run_id`（运行会话）

每启动一次采集 = 一个 run，自增。`runs.config_json` 记录当时的配置。
用于区分"同一天里不同批次"的数据。

## 七、表头变更与自动归档

**问题**：旧版 CSV 是 11 列（无温度），新版是 13 列。直接 `append` 会让同一个文件里出现两种格式。

**规则**：打开当天 CSV 时检查第一行表头，与当前期望的列**逐项比对**：

```
一致  → 原文件继续追加
不一致 → 把旧文件重命名为 YYYY-MM-DD_samples_oldformat.csv（或 _oldformat1/2…）
         再新建文件并写入新表头
```

> 数据**一行都不会丢**，只是被移到归档文件里。
> 你可以在 `D:\IV_data\` 下看到这种文件，确认无误后自行删除。

## 八、关窗校验与补齐

程序正常退出时执行 `verify_and_repair()`：

```
① 比较 COUNT(*) FROM round_log  与  CSV 实际行数
② 相等 → 通过，日志显示 "一致（N 轮）"
③ 不等 → 以数据库为准，用 query_wide() 重建整个 CSV：
         写临时文件 → os.replace 原子替换 → 重新打开继续追加
```

**为什么可能不一致？**
- 程序崩溃/断电 → CSV 少了几行（SQLite 有 WAL，数据还在）
- CSV 写入时磁盘满 → 部分行丢失

**注意**：Windows 不允许替换仍被打开的文件，所以重建前会先关闭 CSV 句柄（这里踩过 `WinError 5` 的坑）。

## 九、持久化策略

| 项目 | 策略 | 效果 |
|---|---|---|
| SQLite journal | `PRAGMA journal_mode=WAL` | 崩溃不损坏，最多回滚最后一个未提交事务 |
| SQLite sync | `PRAGMA synchronous=NORMAL` | 性能与安全折中（WAL 下足够） |
| 提交频率 | **每轮 commit 一次** | 最多丢一轮数据 |
| CSV | **每写一行 flush** | 立刻落盘，可边测边用 Excel 看 |
| 聚合表 | 每轮 flush | 与主数据同步 |

> `-wal` / `-shm` 文件是正常现象，**不要手动删除**。
> 程序正常关闭时会自动 checkpoint 合并进主库。

## 十、常用查询示例

### SQL

```sql
-- ① 某时段 4 路电压（按轮）
SELECT grid_ts, round_id, ch, value
FROM samples
WHERE mode='V' AND grid_ts BETWEEN ? AND ?
ORDER BY grid_ts, ch;

-- ② 电学量 + 温度 联合查询（按轮对齐）
SELECT s.grid_ts, s.ch, s.mode, s.value, e.t1, e.t2, e.dt
FROM samples s
LEFT JOIN env_round e ON s.grid_ts = e.grid_ts
WHERE s.mode='V' AND s.grid_ts BETWEEN ? AND ?;

-- ③ 温差随时间变化（直接用轮表，最快）
SELECT datetime(grid_ts,'unixepoch','localtime') AS t, t1, t2, dt
FROM env_round
WHERE grid_ts BETWEEN ? AND ?
ORDER BY grid_ts;

-- ④ 每小时的温差统计（临时聚合，看趋势）
SELECT datetime(CAST(grid_ts/3600 AS INT)*3600,'unixepoch','localtime') AS hour,
       AVG(dt), MIN(dt), MAX(dt), COUNT(*)
FROM env_round
GROUP BY CAST(grid_ts/3600 AS INT)
ORDER BY hour;

-- ⑤ 检查数据完整性（有多少空轮 / 失败读数）
SELECT SUM(n_bad) AS 总失败数,
       SUM(CASE WHEN n_ok=0 THEN 1 ELSE 0 END) AS 空轮数,
       COUNT(*) AS 总轮数
FROM round_log;

-- ⑥ 找异常电流（超过量程的 90%）
SELECT grid_ts, ch, value FROM samples
WHERE mode='I' AND ABS(value) > 9e-3;
```

### Python / pandas

```python
import pandas as pd, glob, os

# 合并多天的主数据（列结构相同，直接 concat）
files = sorted(glob.glob(r"D:\IV_data\*\*_samples.csv"))
df = pd.concat([pd.read_csv(f, parse_dates=["iso_time"]) for f in files],
               ignore_index=True)
df = df.sort_values("iso_time").reset_index(drop=True)

# 画 ΔT 随驱动电压的变化
df.plot(x="iso_time", y="dt")
```

## 十一、注意事项与已知限制

| 事项 | 说明 |
|---|---|
| **`round_id` 跨天重复** | 它只是"当天第几轮"，全局唯一性请用 `(日期, round_id)` 或 `grid_ts` |
| **CSV 时间只到秒** | 需要毫秒精度查 `samples.ts`。也正因为只到秒，间隔必须 ≥ 1 秒（当前最少 2 秒，满足） |
| **温度只有 2 通道** | `t1`/`t2` 是固定列名，对应 `env_channels` 的前两个通道。若将来接 4 通道温度，需扩展表结构 |
| **`runs` 表跨天为空** | 跨天切库后新库的 `runs` 表是空的，但 `samples.run_id` 仍延续递增（用于追溯，不影响数据） |
| **聚合表不重建** | 若删除 `samples` 里的历史数据，聚合表不会自动同步（聚合只增不减） |
| **`_env.csv` 已废弃** | 温度已并入主 CSV；旧文件保留但不更新 |
| **不要手动编辑 CSV** | 关窗校验会以数据库为准覆盖它 |
| **磁盘占用估算** | 4 通道 × 2 模式 × 3 秒间隔 ≈ 每天 2.9 万轮 → CSV 约 3.5 MB/天、DB 约 24 MB/天（含 WAL 与索引）。7 天约 200 MB |
